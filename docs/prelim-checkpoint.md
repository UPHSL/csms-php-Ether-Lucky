## My T03 Implementation

Resident records are stored in a file-backed SQLite database at `database/database.sqlite`
for development, and `database/testing.sqlite` for automated tests.
`App\Repositories\ResidentRepository` is responsible for persistence. When `save()` is called
it invokes Eloquent's `$resident->save()`, which issues an INSERT into the `residents` table
writes the database-generated primary key back onto the same model instance, so the caller
receives the Resident with its `id` populated. The identifier is produced by the database
through the `$table->id()` auto-incrementing column defined in the migration; no ID is
generated in PHP. `findById()` calls `Resident::find($id)`, which returns the matching model
or `null`. A missing Resident therefore returns `null` rather than throwing, because a
not-found lookup is a normal condition and not an application error.

## My Persistence Design Decision

I decided that `ResidentRepository::save()` should return the same `Resident` instance it was
given, rather than re-fetching the record from the database after the insert.

I implemented it this way because Eloquent already writes the generated primary key back onto
the model object during `save()`. The instance the caller passed in is therefore the same
instance that now carries the `id`, and returning it makes that contract explicit in the method
signature `save(Resident $resident): Resident`.

The alternative I considered was `return Resident::find($resident->id);` — re-reading the row
so the returned object comes straight from the database. I rejected it because it costs an
extra SELECT on every save for no additional guarantee: the in-memory model and the stored row
are identical at that moment. I also considered making `save()` return `void` and letting the
caller read `$resident->id` afterward, but that hides the fact that the object was mutated,
and the ticket asks for the assigned ID to be available on the returned Resident.


## My Migration Design

Migration file: database/migrations/2026_09_01_070716_create_residents_table.php
Primary key design: $table->id() — auto-incrementing big integer, generated by the database
Contact number column type: string(11) — textual, so the leading zero in 09171234567 survives
Status column type: string with a default of 'Active'
Timestamp decision: included via $table->timestamps()

I included timestamps because Eloquent expects `created_at` and `updated_at` unless the model
sets `public $timestamps = false;`. Providing the columns meant the T01 Resident model needed
no changes at all, which was the smaller and safer option.

## Laravel Persistence Behavior I Can Explain

Behavior selected: Eloquent generated IDs via save()

`$model->save()` builds and executes an INSERT, then calls the connection's `lastInsertId()`
and assigns the result to the model's primary key attribute. Because the assignment happens
on the existing object, `$resident->id` is populated immediately after the call returns.
My `ResidentRepository::save()` relies on this: it saves, then returns the same instance,
and `test_a_persisted_resident_receives_a_database_generated_identifier` asserts the id is
null before the call and a positive integer afterward.

## Problem I Encountered

Problem or error:
  In ConfigurationResolver.php line 409:
  The path "database\migrations\*_create_residents_table.php" is not readable.

Cause:
  PowerShell does not expand wildcard patterns when passing arguments to native
  executables. Laravel Pint received the literal string containing the asterisk
  instead of the resolved migration filename.

How I resolved it:
  Passed the actual migration filename to Pint, and confirmed the correct name
  with `ls database/migrations/`. Alternatively `Get-ChildItem` can resolve the
  pattern first, since cmdlets do expand globs.


## My Student-Designed Test

Test name: test_saving_multiple_residents_assigns_distinct_identifiers
What it verifies: Two Residents saved in sequence receive different database identifiers,
each identifier retrieves the correct record, and exactly two rows exist afterward.
Why I chose this scenario: Every one of the seven required tests saves at most a single
Resident, so none of them can detect what happens on the second insert. If `save()` ever
reused an identifier, or updated the existing row instead of inserting a new one, all seven
would still pass while the repository silently lost records. I wanted one test that fails
the moment `save()` stops producing a new row per call — `assertDatabaseCount('residents', 2)`
catches the overwrite case, and `assertNotSame($first->id, $second->id)` catches the
collision case. Sequential ID assignment is also the behavior every later CSMS feature will
depend on, so it seemed like the most valuable single gap to close.
